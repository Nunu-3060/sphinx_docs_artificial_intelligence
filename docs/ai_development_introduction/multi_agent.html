9. マルチエージェントとオーケストレーション

9.1. 本書の定義

マルチエージェントとは、複数のエージェントに作業を分担させる構成である。各エージェントは、それぞれ独立したコンテキスト、指示、ツールを持つ。複数のエージェントの役割分担と作業の流れを設計し、制御することをオーケストレーションという。

これまでの章では、1 つのエージェントが作業する場面を主に扱ってきた。1 つのエージェントで十分な作業は多く、まずは 1 つのエージェントで試すのが基本である。そのうえで、次のような場合にマルチエージェントを検討する。

表 9.1 マルチエージェントを使う理由

理由

内容

コンテキストの分離

大量のファイルを読む調査を別のエージェントに任せ、結果の要約だけを受け取る。主となるエージェントのコンテキストが、調査の途中経過で埋まらない

並列化

互いに独立した作業を同時に進め、全体の所要時間を短くする

専門化

役割ごとに異なる指示、ツール、権限、モデルを与える。例えば、レビュー担当には編集の権限を与えない

相互の検証

実装したエージェントとは別のエージェントにレビューさせる。同じコンテキストで自分の成果物を見直すより、先入観のない確認ができる

9.2. 構成のパターン

複数のモデルの呼び出しやエージェントを組み合わせる構成には、いくつかの典型的なパターンがある [Anthropic-Agents]。代表的なパターンを図 9.1 に示す。

表 9.2 構成のパターン

パターン

内容

開発での例

逐次処理

前の段階の出力を次の段階の入力にする。段階の間に検査を挟める

設計 → 実装 → テストの作成

振り分け

入力の種類を判定し、それに適した担当に振り分ける

問い合わせを不具合・要望・質問に分類し、担当に渡す

並列処理

独立した作業を同時に実行する。同じ作業を複数回実行し、結果を比べる使い方もある

複数のモジュールの同時調査、複数の観点での同時レビュー

オーケストレーター・ワーカー

中心となるエージェントが作業を動的に分割してワーカーに割り当て、結果を統合する

大規模な移行作業を、ファイル単位でワーカーに割り当てる

生成と評価

生成担当が作った成果物を評価担当が批評し、生成担当が改善する

実装担当とレビュー担当の分離

逐次処理、振り分け、並列処理のように、流れをあらかじめコードで決めておく構成は、振る舞いを予測しやすく、検証もしやすい。オーケストレーター・ワーカーのように、作業の分割をモデルが動的に決める構成は柔軟だが、予測しにくい。作業の流れが事前に決められるなら、ワークフローを優先するとよい。

9.3. サンプルコード：オーケストレーター・ワーカー

コード 9.1 は、オーケストレーター・ワーカー型の構成の例である。オーケストレーターは 4 つのファイルの調査をワーカーに割り当て、ワーカーは並列に動く。

コード 9.1 オーケストレーター・ワーカー（ex06_orchestrator.py）
 1"""オーケストレーター・ワーカー型のマルチエージェントの例。
 2
 3オーケストレーターが作業を分割し、ワーカーを並列に動かす。各ワーカーは
 4独立したコンテキスト（会話履歴）で作業し、短い報告だけを返す。オーケストレーターは
 5ファイルの中身を読まずに報告だけを統合するため、自身のコンテキストを節約できる。
 6"""
 7
 8from __future__ import annotations
 9
10from collections.abc import Sequence
11from concurrent.futures import ThreadPoolExecutor
12from dataclasses import dataclass
13
14from llm_stub import Message, Response, RuleBasedLLM, estimate_tokens
15
16SOURCES = {
17    "auth.py": "def login(user, password):\n    # TODO: 試行回数の制限\n    return check(user, password)\n",
18    "order.py": "def total(items):\n    return sum(i.price * i.qty for i in items)\n",
19    "report.py": "def export(rows):\n    # TODO: 文字コードの指定\n    # TODO: 大量データ時の分割\n    pass\n",
20    "util.py": "def clamp(x, lo, hi):\n    return max(lo, min(x, hi))\n",
21}
22
23
24@dataclass(frozen=True)
25class WorkerReport:
26    target: str
27    summary: str
28    context_tokens: int
29
30
31def worker_rule(system: str, messages: Sequence[Message]) -> Response:
32    """模擬ワーカー：渡されたソースの TODO を数えて報告する。"""
33    source = messages[-1].content
34    todos = [line.split("TODO:")[1].strip() for line in source.splitlines() if "TODO:" in line]
35    if not todos:
36        return Response("未完了の作業なし")
37    return Response(f"未完了 {len(todos)} 件: " + "、".join(todos))
38
39
40def run_worker(target: str) -> WorkerReport:
41    """1 つのファイルを担当するワーカー。独自のコンテキストを持つ。"""
42    llm = RuleBasedLLM(worker_rule)
43    system = "あなたはコード調査の担当者である。未完了の作業を短く報告せよ。"
44    messages = [Message("user", SOURCES[target])]
45    response = llm.complete(system, messages)
46    used = estimate_tokens(system) + sum(estimate_tokens(m.content) for m in messages)
47    return WorkerReport(target, response.text, used)
48
49
50def orchestrate(targets: Sequence[str]) -> str:
51    with ThreadPoolExecutor(max_workers=4) as pool:
52        reports = list(pool.map(run_worker, targets))
53    for r in reports:
54        print(f"ワーカー {r.target:<10} コンテキスト {r.context_tokens:>3} トークン -> {r.summary}")
55    summary = "\n".join(f"- {r.target}: {r.summary}" for r in reports)
56    print(f"オーケストレーターが受け取った報告: {estimate_tokens(summary)} トークン")
57    return summary
58
59
60def main() -> None:
61    print(orchestrate(sorted(SOURCES)))
62
63
64if __name__ == "__main__":
65    main()

  • run_worker（40 〜 47 行目）は、ワーカーごとに新しいクライアントと会話履歴を作る。つまり、各ワーカーは独立したコンテキストで作業する。

  • orchestrate（50 〜 57 行目）は、ThreadPoolExecutor でワーカーを並列に動かし、報告だけを統合する。

実行結果は次のとおりである。4 つのワーカーのコンテキストは合計 212 トークンだが、オーケストレーターが受け取るのは 64 トークンの報告だけである。実際の作業では、ワーカーが読むファイルは数万トークンになることもあり、この差はさらに大きくなる。

コード 9.2 ex06_orchestrator.py の出力
1ワーカー auth.py    コンテキスト  57 トークン -> 未完了 1 件: 試行回数の制限
2ワーカー order.py   コンテキスト  48 トークン -> 未完了の作業なし
3ワーカー report.py  コンテキスト  62 トークン -> 未完了 2 件: 文字コードの指定、大量データ時の分割
4ワーカー util.py    コンテキスト  45 トークン -> 未完了の作業なし
5オーケストレーターが受け取った報告: 64 トークン
6- auth.py: 未完了 1 件: 試行回数の制限
7- order.py: 未完了の作業なし
8- report.py: 未完了 2 件: 文字コードの指定、大量データ時の分割
9- util.py: 未完了の作業なし

9.4. 開発での使い方

コーディングエージェントでマルチエージェントを使う代表的な場面は、次のとおりである。

  • 調査の委任：「このリポジトリで認証がどう実装されているか調べて」のような、多くのファイルを読む調査をサブエージェントに任せる。主となるエージェントは結論だけを受け取る。

  • 独立した観点でのレビュー：実装が終わったら、実装の経緯を知らないレビュー担当のサブエージェントに差分を確認させる。仕様との照合（仕様駆動開発）を専門に行うエージェントを作るのも有効である。

  • 並列の実装：互いに独立した作業（別々のモジュールの改修など）を、複数のエージェントに同時に進めさせる。各エージェントが同じファイルを同時に書き換えて衝突しないよう、Git の worktree などで作業場所を分ける。

  • 大規模な定型作業：多数のファイルに同じ種類の変更（API の移行など）を加える作業を、ファイル単位に分割して並列に処理する。

Claude Code での具体的な方法は実践：Claude Code で示す。

9.5. 注意点

  • 費用が増える：エージェントの数だけモデルを呼ぶため、トークンの消費が大きく増える。Anthropic の報告では、エージェントは通常の対話の約 4 倍、マルチエージェントは約 15 倍のトークンを消費した [Anthropic-MultiAgent]。作業の価値が費用に見合うかを考える。

  • 情報が欠落する：ワーカーの報告は要約であり、オーケストレーターには細部が伝わらない。報告に含めるべき項目（根拠となるファイル名と行番号など）を指示しておく。

  • 調整が難しい：互いに依存する作業を複数のエージェントに分けると、前提の食い違いや、同じファイルへの変更の衝突が起きる。前述の Anthropic の報告では、コーディングの作業は調査の作業に比べて、真に並列化できる部分が少ないことも指摘されている [Anthropic-MultiAgent]。

  • 全体の把握が難しくなる：エージェントが増えるほど、誰が何をしたかを人間が追いにくくなる。各エージェントの作業の記録を残し、最終的な統合と確認は 1 か所で行う。

分担の基本は、「読み取りは並列に、書き込みは慎重に」である。調査やレビューのような読み取り中心の作業は並列化しやすく、効果も大きい。書き込みを伴う作業は、互いに独立していることを確かめてから並列化する。
