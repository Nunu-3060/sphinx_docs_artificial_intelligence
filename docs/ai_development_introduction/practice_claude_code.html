12. 実践：Claude Code

本章では、Anthropic のコーディングエージェントである Claude Code を題材に、これまでの章で説明した手法を実際に適用する方法を示す。Claude Code の機能は頻繁に更新されるため、詳細は公式文書 [ClaudeCode-Docs] で確認してほしい。本章の内容は、2026 年 10 月時点の情報に基づく。

12.1. Claude Code の概要

Claude Code は、利用者が自然言語で依頼すると、ソースコードを読み、コマンドを実行し、ファイルを編集しながら作業を進めるエージェントである。ターミナル、VS Code や JetBrains 系の IDE、デスクトップアプリ、Web ブラウザから使える。作業したいプロジェクトのディレクトリで claude コマンドを実行すると、対話画面が始まる。

Claude Code の主な機能を、本書の 4 つの層に対応付けると表 12.1 のようになる。

表 12.1 Claude Code の機能と本書の各層の対応

層

Claude Code の機能

プロンプト

依頼の文面

コンテキスト

CLAUDE.md、@ によるファイルの参照、スキル、/clear、/compact、/context、サブエージェント

ハーネス

権限の設定、フック、サンドボックス、MCP サーバー、settings.json

ループ

計画モード（計画の承認）、Stop フック、/goal、/loop、claude -p による非対話の実行、GitHub Actions

本章では、注文管理の Web API（Python、FastAPI）を開発する架空のプロジェクトを例に、これらを順に設定していく。

12.2. コンテキストを整える

12.2.1. CLAUDE.md

CLAUDE.md は Claude Code の規約ファイルであり、セッションの開始時に自動的に読み込まれる [ClaudeCode-Memory]。

表 12.2 CLAUDE.md の主な置き場所

場所

用途

プロジェクト直下の CLAUDE.md

プロジェクト固有の情報。リポジトリに含めてチームで共有する

サブディレクトリの CLAUDE.md

そのディレクトリ配下で作業するときにだけ必要な情報

~/.claude/CLAUDE.md

すべてのプロジェクトに共通する個人の好み

/init コマンドを実行すると、Claude Code がプロジェクトを調査して CLAUDE.md の雛形を作る。雛形をもとに、コンテキストエンジニアリングで述べた「コードを読むだけでは分からないこと」を追記していく。コード 12.1 は記述の例である。

コード 12.1 CLAUDE.md の例（CLAUDE.sample.md）
 1# 注文管理 API
 2
 3FastAPI で作った注文管理の Web API。DB は PostgreSQL。
 4
 5## よく使うコマンド
 6
 7- テスト: `python -m pytest -q`（DB を使うテストは先に `docker compose up -d db`）
 8- 静的解析: `flake8 src tests` と `mypy src`
 9- 開発サーバー: `uvicorn app.main:app --reload`
10
11## 規約
12
13- 型ヒントを必ず書く。mypy の strict モードを通すこと
14- DB へのアクセスは `src/app/repositories/` に閉じ込め、API 層から直接 SQL を書かない
15- 金額は `Decimal` で扱う。`float` を使わない
16
17## 作業の進め方
18
19- 実装の前に、変更方針を箇条書きで示して確認を取る
20- 振る舞いを変えたらテストを追加し、`python -m pytest -q` が成功するまで修正する
21- 仕様は `docs/specs/` にある。仕様と実装が食い違ったら、実装せずに報告する
22
23## してはいけないこと
24
25- `migrations/` 配下の既存ファイルを編集しない（新しいマイグレーションを追加する）
26- `.env` を読まない、コミットしない

規約には理由を添え（15 行目では、金額に Decimal を使う規則）、作業の進め方（19 〜 21 行目）と、してはいけないこと（25 〜 26 行目）を明示している。21 行目の「仕様と実装が食い違ったら報告する」は、仕様駆動開発で述べた仕様と実装の同期のための指示である。

12.2.2. コンテキストの管理

表 12.3 コンテキストの管理に使うコマンド

コマンド

内容

/context

現在のコンテキストの使用状況を、要素ごとに表示する

/clear

会話の履歴を消去し、新しい会話を始める。別の作業に移るときに使う

/compact

これまでの会話を要約して、コンテキストを空ける。作業を続けたまま整理したいときに使う

/memory

/rewind

会話やファイルの変更を、過去の時点に巻き戻す

コンテキストエンジニアリングで述べたとおり、最も効果的なのは作業ごとに /clear で会話を分けることである。また、AI が誤った前提で作業を重ねてしまったときは、誤りを指摘し続けるより、/rewind で誤る前の時点に戻すか、/clear でやり直すほうが早い。

12.2.3. スキル

スキルは、特定の作業の手順や知識をまとめたものである [ClaudeCode-Skills]。.claude/skills/<スキル名>/SKILL.md に置くと、Claude は関連する作業を頼まれたときにスキルを読み込み、その手順に従う。/<スキル名> で明示的に呼び出すこともできる。

コード 12.2 スキルの例（SKILL.sample.md）
 1---
 2name: add-endpoint
 3description: 注文管理 API に新しいエンドポイントを追加する手順。API の追加や変更を頼まれたときに使う。
 4---
 5
 6# エンドポイントの追加手順
 7
 81. `docs/specs/` に仕様書があるか確認する。なければ作業を止めて、仕様書の作成を提案する
 92. `src/app/schemas/` にリクエストとレスポンスの Pydantic モデルを追加する
103. `src/app/repositories/` に DB アクセスを追加する
114. `src/app/routers/` にエンドポイントを追加する
125. `tests/api/` に正常系と異常系（400、404）のテストを追加する
136. `python -m pytest -q tests/api` と `mypy src` が成功するまで修正する
147. `docs/api.md` のエンドポイント一覧を更新する

先頭の name と description（2 〜 3 行目）は常に Claude に示され、Claude はこの説明を見てスキルを使うかどうかを判断する。本文は使うときにだけ読み込まれる。コンテキストエンジニアリングで述べた「情報を段階的に見せる」方法であり、多くのスキルを用意してもコンテキストを圧迫しない。毎回必要な情報は CLAUDE.md に、特定の作業のときだけ必要な手順はスキルに書く、と使い分ける。

12.3. 依頼の進め方

Claude Code に大きな作業を任せるときは、「調査 → 計画 → 実装 → 検証 → コミット」の順に進める [ClaudeCode-BestPractices]。

計画の段階では計画モードを使う。計画モードでは、Claude はファイルを変更せずに調査と計画だけを行う。Shift + Tab キーで権限モードを切り替えるか、/plan コマンドで計画モードに入る。計画を確認して合意したら、通常のモードに戻して実装を依頼する。これはループエンジニアリングで述べた「計画の承認」の時点で人間が関与する方法である。

コード 12.3 計画モードでの依頼の例
1/plan docs/specs/order-cancel.md の仕様を実装したい。
2関係する既存のコードを調べ、仕様書の「実装計画」のタスク T1 〜 T4 それぞれについて、
3変更するファイルと変更内容を示して。不明な点があれば質問して。

計画に合意したら、タスクを 1 つずつ依頼する。

コード 12.4 実装の依頼の例
1計画どおり T2 を実装して。受け入れ条件 4 と 5 に対応するテストも追加し、
2python -m pytest -q と mypy src が成功するまで修正すること。既存のテストは変更しないこと。
3終わったら、変更したファイル、確認したこと、未確認のことを報告して。

1 行目で対象と範囲を、2 行目で完了条件を、3 行目で報告の形式を示している。プロンプトエンジニアリングで述べた要素がそろっていることを確認してほしい。

12.4. ハーネスを整える

12.4.1. 権限モード

Claude Code が利用者の許可なしにどこまで操作してよいかは、権限モードで切り替える [ClaudeCode-Permissions]。

表 12.4 主な権限モード

モード

内容

default

ファイルの編集やコマンドの実行のたびに許可を求める

acceptEdits

ファイルの編集は許可なしで行い、コマンドの実行には許可を求める

plan

調査と計画だけを行い、ファイルの変更や、変更を伴うコマンドの実行はしない

auto

安全と判断された操作は自動で実行し、危険の可能性がある操作は止める

dontAsk

設定ファイルで事前に許可した操作だけを実行し、それ以外は確認せずに拒否する。無人で動かす自動化向けである

bypassPermissions

ほぼすべての操作を許可なしで実行する。コンテナや仮想マシンなどの隔離された環境以外では使わない

12.4.2. 権限の設定とフック

権限の規則とフックは settings.json に書く [ClaudeCode-Settings]。プロジェクトの .claude/settings.json に書けばチームで共有でき、.claude/settings.local.json に書けば自分だけに適用される。

コード 12.5 settings.json の例（settings.sample.json）
 1{
 2  "permissions": {
 3    "allow": [
 4      "Bash(pytest *)",
 5      "Bash(python -m pytest *)",
 6      "Bash(flake8 *)",
 7      "Bash(mypy *)",
 8      "Bash(git diff *)",
 9      "Bash(git status)"
10    ],
11    "deny": [
12      "Read(./.env)",
13      "Read(./secrets/**)",
14      "Bash(git push *)"
15    ]
16  },
17  "hooks": {
18    "PostToolUse": [
19      {
20        "matcher": "Edit|Write",
21        "hooks": [
22          {
23            "type": "command",
24            "command": "python -m flake8 src tests 1>&2 || exit 2"
25          }
26        ]
27      }
28    ],
29    "Stop": [
30      {
31        "hooks": [
32          {
33            "type": "command",
34            "command": "python .claude/hooks/stop_hook_run_tests.py"
35          }
36        ]
37      }
38    ]
39  }
40}

  • permissions の allow（3 〜 10 行目）には許可なしで実行してよい操作を、deny（11 〜 15 行目）には禁止する操作を書く。この例では、テスト、静的解析、差分の確認を許可し、秘密情報の読み取りと git push を禁止している。

  • hooks の PostToolUse（18 〜 28 行目）は、ファイルを編集するたびに flake8 を実行するフックである。コマンドが終了コード 2 で終わると、標準エラー出力の内容が Claude に伝えられる。flake8 が違反を検出すると終了コード 2 を返すようにしているため（24 行目）、Claude は違反の内容を読んで修正する。

  • Stop（29 〜 38 行目）は、後述するループのためのフックである。

フックには、ほかにも次のような種類がある [ClaudeCode-Hooks]。

表 12.5 主なフックの種類

種類

実行される時点

PreToolUse

ツールを使う直前。ツールの使用を止めることもできる

PostToolUse

ツールを使った直後。整形ツールや静的解析の実行に使う

UserPromptSubmit

利用者が依頼を送信したとき

Stop

Claude が応答を終えようとしたとき。作業を続けさせることもできる

SubagentStop

サブエージェントが応答を終えようとしたとき

SessionStart

セッションを開始したとき

CLAUDE.md に書いた指示は Claude が判断して従うものだが、フックは必ず実行される。ハーネスエンジニアリングで述べたとおり、例外なく守らせたい規則はフックで実現する。

12.4.3. MCP サーバーとサンドボックス

MCP サーバーを登録すると、課題管理サービスやデータベース、ブラウザなどを Claude Code から操作できる [ClaudeCode-MCP]。例えば課題管理サービスの MCP サーバーを登録すれば、「課題 123 の内容を読んで仕様書の案を作って」のような依頼ができる。

また、/sandbox コマンドでサンドボックスを有効にすると、Claude が実行するコマンドのファイルシステムやネットワークへのアクセスを制限できる（対応している環境のみ）。

12.5. ループを組む

12.5.1. Stop フックによる自己修正のループ

コード 12.5 の Stop フックは、Claude が作業を終えようとしたときにコード 12.6 のスクリプトを実行する。

コード 12.6 テストが成功するまで作業を続けさせる Stop フック（stop_hook_run_tests.py）
 1"""Claude Code の Stop フックとして使い、テストが成功するまで作業を続けさせるスクリプト。
 2
 3Claude が応答を終えようとしたときに pytest を実行する。失敗したテストがあれば
 4``{"decision": "block", "reason": ...}`` を出力し、Claude に作業を続けさせる。
 5
 6``stop_hook_active`` が真のときは、すでにこのフックによって作業を続けている。
 7この場合は終了を止めない。テストがいつまでも成功しない場合に、ループが
 8終わらなくなるのを防ぐためである。
 9"""
10
11from __future__ import annotations
12
13import json
14import subprocess
15import sys
16
17
18def main() -> int:
19    hook_input = json.load(sys.stdin)
20    if hook_input.get("stop_hook_active"):
21        return 0
22
23    result = subprocess.run(
24        [sys.executable, "-m", "pytest", "-q", "--no-header"],
25        cwd=hook_input.get("cwd"),
26        capture_output=True,
27        text=True,
28        timeout=600,
29    )
30    if result.returncode == 0:
31        return 0
32
33    tail = "\n".join(result.stdout.splitlines()[-20:])
34    decision = {
35        "decision": "block",
36        "reason": f"テストが失敗している。原因を調べて修正し、再度 pytest を実行すること。\n{tail}",
37    }
38    print(json.dumps(decision, ensure_ascii=False))
39    return 0
40
41
42if __name__ == "__main__":
43    sys.exit(main())

スクリプトは pytest を実行し（23 〜 29 行目）、失敗したテストがあれば {"decision": "block", "reason": ...} を出力する（34 〜 38 行目）。decision が block のとき、Claude は終了せず、reason の内容を読んで作業を続ける。つまり、「テストがすべて成功するまで終わらない」という完了条件を、Claude の判断に任せず、仕組みとして強制している。

ただし、ループエンジニアリングで述べたとおり、ループには終了条件が必要である。テストがいつまでも成功しない場合に備え、このスクリプトは、フックによってすでに作業を続けている状態（stop_hook_active が真）では終了を止めない（20 〜 21 行目）。これにより、フックによる差し戻しは 1 回までになる。より多く差し戻したい場合は、回数をファイルに記録するなどして上限を設ける。

12.5.2. /goal と /loop

フックの設定を書かずに、同様のループを手軽に作る方法もある。

  • /goal コマンドに条件を与えると、Claude はその条件を満たすまで、ターンをまたいで作業を続ける。例えば /goal python -m pytest -q がすべて成功するのように使う。

  • /loop コマンドは、指示を一定の間隔で繰り返し実行する。例えば /loop 5m デプロイが完了したか確認してのように、外部の状態の監視に使う。

12.5.3. 非対話の実行と CI

-p オプションを付けると、Claude Code を対話画面なしで実行し、結果を標準出力に出力できる [ClaudeCode-Headless]。シェルスクリプトや CI に組み込めるため、ループエンジニアリングで述べた外側のループを自動化できる。

コード 12.7 非対話の実行の例
1$ # 結果を JSON で受け取り、jq で処理する
2$ claude -p "直近のコミットの変更点を要約して" --output-format json | jq -r .result
3
4$ # 許可するツールと、反復・費用の上限を指定して実行する
5$ claude -p "tests/ の失敗しているテストを直して" \
6    --allowedTools "Read,Edit,Bash(python -m pytest *)" \
7    --max-turns 30 --max-budget-usd 5

7 行目の --max-turns と --max-budget-usd は、それぞれ反復の回数と費用の上限を指定する。無人で動かす場合は、ループエンジニアリングで述べたとおり、必ずこうした上限を設ける。

GitHub Actions と連携すると、プルリクエストや課題のコメントで Claude に依頼し、レビューや修正を任せることもできる [ClaudeCode-GitHubActions]。

12.6. マルチエージェントを使う

12.6.1. サブエージェント

Claude Code は、作業の一部をサブエージェントに任せられる [ClaudeCode-Subagents]。サブエージェントはメインの会話とは別のコンテキストで作業し、結果だけを返す。独自のサブエージェントは .claude/agents/<名前>.md に定義する。

コード 12.8 サブエージェントの例（agent.sample.md）
 1---
 2name: spec-reviewer
 3description: 実装が仕様書を満たしているかを確認する。実装が終わった後、コミットの前に使う。
 4tools: Read, Grep, Glob, Bash
 5model: sonnet
 6---
 7
 8あなたは仕様と実装の対応を確認するレビュー担当者である。
 9
101. 依頼で指定された仕様書（`docs/specs/` 配下）を読み、受け入れ条件を一覧にする
112. `git diff` で変更内容を確認する
123. 受け入れ条件ごとに、満たしているか・テストで確認されているかを判定する
134. 結果を次の形式で報告する。ファイルは編集しない
14
15| 受け入れ条件 | 判定 | 根拠（ファイル名と行番号） |

この例は、実装が仕様書を満たしているかを確認するレビュー担当である。tools（4 行目）で Edit や Write を与えず、本文（13 行目）でも編集しないよう指示している。ただし、Bash を与えているため、コマンドによる変更は技術的には可能である。厳密に禁止したい場合は、権限の設定で禁止する。model（5 行目）では、作業に応じたモデルを指定できる。マルチエージェントとオーケストレーションで述べた「専門化」と「相互の検証」の例である。

12.6.2. 並列の作業

  • claude --worktree <名前>（または -w）で起動すると、Git の worktree を作り、隔離された作業場所で Claude Code を動かせる。複数の Claude Code を同時に動かしても、互いの変更が衝突しない。

  • /batch コマンドは、大規模な変更を独立した作業に分割し、計画を示したうえで、承認後に複数のエージェントで並列に処理する。

12.7. ハーネスを改善し続ける

最後に、ループエンジニアリングで述べたハーネス改善のループを Claude Code で回す方法をまとめる。

  1. Claude が誤った振る舞いをしたら、その場で直させるだけでなく、原因を考える。

  2. 情報の不足が原因なら CLAUDE.md やスキルに追記する。規則が守られなかったのが原因なら、フックや権限の設定で強制する。検証の不足が原因なら、テストやリンターの規則を追加する。

  3. 変更をリポジトリにコミットし、チームで共有する。

  4. 同じ種類の作業で効果を確かめる。重要な変更であれば、評価駆動開発の方法で、claude -p を使って同じ課題を複数回実行し、変更前後の成功率を比べる。

このループを続けることで、Claude Code はそのプロジェクトに特化した、信頼できる開発の担い手になっていく。
