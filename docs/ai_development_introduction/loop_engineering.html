6. ループエンジニアリング

6.1. 本書の定義

AI による開発は、1 回の指示と 1 回の応答では終わらない。モデルはツールを呼んで結果を読み、コードを書いてはテストを実行し、人間のレビューを受けて直す。このような反復の構造、つまり「何を、どの順で、何回繰り返し、何をもって止め、どこで人間が関与するか」を設計する技術を、本書ではループエンジニアリングと呼ぶ。

「ループエンジニアリング」は、プロンプトエンジニアリングなどと比べて新しい呼び名であり、定義が定まっているとはいえない。ただし、その中身である「エージェントループ」「自己修正」「Human-in-the-loop」「制御ループ（steering loop）」といった考え方は、それぞれ広く議論されている [Bockeler2026]。本書では、これらを反復の設計という観点でまとめて扱う。

ハーネスエンジニアリングが「どんな道具と検証手段を用意するか」を扱うのに対し、ループエンジニアリングは「それらをどう組み合わせて反復させるか」を扱う。同じテストという道具でも、いつ実行し、失敗したら何回まで直させ、どの時点で人間に判断を仰ぐかによって、結果の品質と費用は大きく変わる。

6.2. ループの階層

AI による開発の反復は、図 6.1 のように、時間の尺度が異なる複数のループが入れ子になっていると捉えられる。

6.3. エージェントループ

最も内側のループは、ハーネスエンジニアリングのコード 5.1 で示したエージェントループである。モデルが推論し、ツールを呼び、結果を読み、再び推論する。推論と行動を交互に行わせるこの方式は ReAct として知られる [Yao2022]。

このループはエージェント製品に組み込まれているため、利用者が直接設計する機会は少ない。利用者が設計するのは、主に次の点である。

  • 反復の上限：無人で動かす場合は、反復の回数、時間、費用に上限を設ける。

  • ツールの結果の分かりやすさ：結果やエラーメッセージが分かりやすければ、少ない反復で目的に到達する。

6.4. 自己修正のループ

コードを書き、検証し、失敗すれば直す。このループを AI 自身に回させることが、AI による開発の品質を上げる最も効果的な方法である。モデルが自分の出力を検証結果や自己批評をもとに改善する手法は、Self-Refine や Reflexion などとして研究されている [Madaan2023] [Shinn2023]。

ループの品質は、検証の品質で決まる。検証が甘ければ、誤ったコードが「成功」として通過する。検証が不安定であれば、正しいコードを何度も直すことになる。自己修正のループを設計するときは、まず検証の手段（ハーネスエンジニアリングのセンサー）を整える。

6.4.1. サンプルコード：自己修正のループ

コード 6.1 は、テストの結果をモデルに返して修正させる自己修正のループである。

コード 6.1 自己修正のループ（ex04_fix_loop.py）
 1"""テストの結果をモデルに返して修正させる、自己修正ループの例。
 2
 3ループは次のいずれかで終了する。
 4
 5* すべてのテストが成功した（成功）
 6* 前回と同じテストが同じ理由で失敗した（行き詰まり）
 7* 最大反復回数に達した（打ち切り）
 8
 9注意: 生成されたコードを exec で実行している。実際のシステムでは、
10コンテナなどの隔離された環境で実行すること。
11"""
12
13from __future__ import annotations
14
15from collections.abc import Sequence
16from dataclasses import dataclass
17from typing import Literal
18
19from llm_stub import LLMClient, Message, Response, RuleBasedLLM
20
21Outcome = Literal["success", "stalled", "max_iterations"]
22
23TEST_CASES: list[tuple[int, bool]] = [(2024, True), (2023, False), (1900, False), (2000, True)]
24
25
26@dataclass(frozen=True)
27class LoopResult:
28    outcome: Outcome
29    iterations: int
30    code: str
31
32
33def run_tests(code: str) -> list[str]:
34    """コードを実行し、失敗したテストの説明の一覧を返す。空なら全件成功。"""
35    namespace: dict[str, object] = {}
36    try:
37        exec(code, namespace)
38    except Exception as e:  # 生成コードはどんな例外でも起こしうる
39        return [f"コードを実行できない: {e!r}"]
40    func = namespace.get("is_leap_year")
41    if not callable(func):
42        return ["関数 is_leap_year が定義されていない"]
43    failures = []
44    for year, expected in TEST_CASES:
45        actual = func(year)
46        if actual != expected:
47            failures.append(f"is_leap_year({year}) は {expected} であるべきだが {actual} を返した")
48    return failures
49
50
51def fix_loop(llm: LLMClient, task: str, max_iterations: int = 5) -> LoopResult:
52    messages: list[Message] = [Message("user", task)]
53    previous_failures: list[str] | None = None
54    code = ""
55    for i in range(1, max_iterations + 1):
56        code = llm.complete("Python のコードだけを出力せよ。", messages).text
57        messages.append(Message("assistant", code))
58        failures = run_tests(code)
59        print(f"--- 反復 {i}: 失敗 {len(failures)} 件")
60        for f in failures:
61            print(f"    {f}")
62        if not failures:
63            return LoopResult("success", i, code)
64        if failures == previous_failures:
65            return LoopResult("stalled", i, code)
66        previous_failures = failures
67        feedback = "テストが失敗した。原因を考えて修正したコード全体を出力せよ。\n" + "\n".join(failures)
68        messages.append(Message("user", feedback))
69    return LoopResult("max_iterations", max_iterations, code)
70
71
72# ---- モデルの代わり：フィードバックの内容に応じて、段階的に正しいコードへ近づく ----
73
74ATTEMPTS = [
75    "def is_leap_year(year):\n    return year % 4 == 0\n",
76    "def is_leap_year(year):\n    return year % 4 == 0 and year % 100 != 0\n",
77    "def is_leap_year(year):\n    return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)\n",
78]
79
80
81def fixer_rule(system: str, messages: Sequence[Message]) -> Response:
82    feedback_count = sum(1 for m in messages if m.role == "user") - 1
83    return Response(ATTEMPTS[min(feedback_count, len(ATTEMPTS) - 1)])
84
85
86def main() -> None:
87    result = fix_loop(RuleBasedLLM(fixer_rule), "西暦 year がうるう年かを返す関数 is_leap_year を書け。")
88    print(f"結果: {result.outcome}（{result.iterations} 回）")
89    print(result.code)
90

92if __name__ == "__main__":
93    main()

  • run_tests（33 〜 48 行目）は、生成されたコードを実行し、失敗したテストの説明を返す。この説明がモデルへのフィードバックになるため、「何を入力し、何を期待し、何が返ったか」を具体的に書いている。

  • fix_loop（51 〜 69 行目）は、成功・行き詰まり・上限の 3 つの終了条件を持つ。前回とまったく同じ失敗が続いた場合は、それ以上反復しても改善しないと判断して止める（64 〜 65 行目）。

実行結果は次のとおりである。1 回目と 2 回目の失敗の説明を受けて、3 回目で正しい実装にたどり着いている。

6.5.1. 完了条件の抜け道に注意する

モデルは与えられた完了条件を満たそうとする。そのため、完了条件に抜け道があると、本来の目的を果たさずに条件だけを満たすことがある。例えば、「テストがすべて成功するまで直す」とだけ指示すると、実装を直す代わりに、失敗したテストを削除したり、期待値を書き換えたり、特定の入力だけを特別扱いしたりすることがある。

対策として、次のような方法がある。

  • テストを変更してはいけないことを明示する。フックや権限の設定で、テストファイルへの書き込みを禁止する。

  • 完了条件を複数の観点で定める（テストの成功に加え、型検査とリンターの成功、変更範囲の制限など）。

  • 最終的な差分を、人間または別のエージェントがレビューする。

6.6. 人間のループ

人間がどこでループに関与するか（Human-in-the-loop）は、品質と効率の釣り合いで決める。すべての操作を人間が承認すれば安全だが、AI に任せる意味が薄れる。逆に、すべてを任せれば速いが、誤った方向に進んだまま長時間作業してしまう危険がある。

関与の時点として効果的なのは、次の 3 つである。

  1. 計画の承認：実装を始める前に、AI に計画を立てさせ、人間が確認する。方向の誤りを最も安く修正できる時点である。

  2. 差分のレビュー：作業の区切りで、変更の差分を確認する。コミットやプルリクエストの単位が目安になる。

  3. 取り消せない操作の承認：本番環境への反映、データの削除、外部への送信などは、必ず人間が承認する。

人間の関与を効果的にするには、AI からの報告の形式を整えておくとよい。例えば、「何を変えたか」「なぜそう変えたか」「何を確かめたか」「何が未確認か」を必ず報告させれば、レビューの負担が減り、見落としも防げる。

6.7. 長時間・自律的なループ

検証の手段が整っていれば、人間が常に見ていなくても、AI に長時間作業を続けさせられる。このような使い方では、次の工夫が必要になる。

  • 進捗を外部に記録する：作業の一覧、完了した項目、決定事項をファイルに記録させる（コンテキストエンジニアリングの「外部の記憶」参照）。

  • 1 回の反復を小さくする：1 回の反復では 1 つの項目だけに取り組ませ、検証してから記録させる。一度に多くを変えると、失敗の原因が分からなくなる。

  • 同じ指示を繰り返し与える：同じプロンプトを繰り返し与え、毎回ファイルに記録された進捗から次の作業を選ばせる方式もある。この方式は「Ralph ループ」とも呼ばれる [Huntley2025]。仕組みは単純だが、仕様書と検証の手段が整っていることが前提になる。

  • 目標の達成まで続けさせる：エージェントが作業を終えようとしたとき、完了条件を満たしているかを確認し、満たしていなければ作業を続けさせる。Claude Code では、Stop フックや /goal コマンドでこれを実現できる（実践：Claude Code 参照）。

自律的なループは、人間の監督が減る分、ハーネスエンジニアリングで述べた権限とサンドボックスによる安全対策が特に重要になる。

6.8. ハーネス改善のループ

最も外側のループは、AI の失敗から学び、ハーネスを改善するループである。

  1. AI が誤った振る舞いをしたら、それを記録する。

  2. 同じ誤りを防ぐ仕組みを作る。規約ファイルへの追記、リンターの規則の追加、ツールの追加、フックの追加などである。

  3. 改善の効果を確かめる。

3 つ目の「効果を確かめる」を勘に頼ると、規約ファイルが肥大化するばかりで、どの追記が効いているのか分からなくなる。効果を定量的に確かめる方法は評価駆動開発で扱う。また、複数のループを並列に動かす方法はマルチエージェントとオーケストレーションで扱う。
