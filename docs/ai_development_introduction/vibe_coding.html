10. Vibe Coding と規律ある AI 開発

10.1. 本書の定義

Vibe Coding とは、AI が生成したコードの中身をほとんど読まず、動かしてみた結果だけを見ながら、対話で AI に修正を頼み続ける開発の仕方である。2025 年 2 月に Andrej Karpathy が SNS への投稿で使い、広まった言葉である。本来は「コードの存在を忘れ、雰囲気（vibe）に身を任せる」という、遊びの試作を念頭に置いた言葉だった [Willison2025]。

これに対し、本書がここまで述べてきたのは、AI に多くの作業を任せつつも、仕様、検証、レビューによって品質を担保する開発である。本書ではこれを「規律ある AI 開発」と呼び、Vibe Coding と対比する。「エージェント型エンジニアリング（agentic engineering）」などと呼ばれることもある。

両者は、どちらが正しいかではなく、目的に応じて使い分けるものである。

10.3. Vibe Coding の価値と限界

Vibe Coding には明確な価値がある。プログラミングの経験が浅い人でも自分の道具を作れるし、経験のあるエンジニアにとっても、アイデアを数分で形にして確かめられるのは大きな利点である。何を作るべきかが分からない段階では、仕様を書くより、試作を触ってみるほうが早く答えにたどり着ける。

一方で、Vibe Coding で作ったものをそのまま製品にすると、次のような問題が起きやすい。

  • 規模の壁：コードが大きくなると、AI も全体を把握できなくなり、ある箇所を直すと別の箇所が壊れる状態に陥る。誰もコードを理解していないため、人間が介入して立て直すことも難しい。

  • 見えない欠陥：画面上は正しく動いていても、入力の検証の漏れ、認証の不備、秘密情報の埋め込みなどの欠陥は、動かして見るだけでは発見できない。

  • 保守の困難：設計の意図が残っていないため、後から機能を追加したり、不具合を直したりするのが難しい。

10.4. 使い分けの指針

次の問いに 1 つでも「はい」と答えるなら、規律ある AI 開発の手法（仕様、テスト、レビュー）を取り入れる。

  • そのコードを、自分以外の人が使う、または保守するか。

  • そのコードを、数週間以上使い続けるか。

  • そのコードが、個人情報、金銭、認証、外部に公開されるシステムに関わるか。

  • そのコードの不具合が、誰かに損害を与えうるか。

すべて「いいえ」であれば、Vibe Coding で十分なことも多い。

また、両者は段階的につなげられる。まず Vibe Coding で試作し、方向性が固まったら、試作から得た知見をもとに仕様書を書き（仕様駆動開発）、本番用のコードはテストとレビューを伴って作り直す。試作のコードをそのまま本番に流用しないことが重要である。

10.5. 人間に求められる能力

AI に任せる範囲が広がるほど、人間に求められる能力は「コードを書く力」から次のような力に移っていく。

  • 何を作るべきかを決める力：要求を明確にし、検証できる受け入れ条件に落とし込む。

  • 良し悪しを見分ける力：AI が出した設計やコードの問題点に気付く。そのためには、自分で設計し、コードを書いた経験が欠かせない。

  • 仕組みを作る力：AI が誤りに自分で気付ける検証の仕組みや、誤りを繰り返さないための規約を整える。

Vibe Coding だけを続けていると、2 つ目の「良し悪しを見分ける力」が育たない。この点はリスクと品質管理で改めて扱う。
