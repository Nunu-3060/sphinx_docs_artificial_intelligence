5. ハーネスエンジニアリング

5.1. 本書の定義

ハーネスとは、エージェントのうちモデル以外のすべて、つまりモデルを動かすための道具・実行環境・制約・検証の仕組みを指す。「エージェント = モデル + ハーネス」と表現されることもある [Bockeler2026]。ハーネスエンジニアリングとは、このハーネスを設計し、改善する技術である。

ハーネスという言葉は、もとは馬具（馬の力を荷車に伝え、向きを制御する道具）を意味する。モデルという強力だが気まぐれな力を、目的の方向に安全に引き出すための仕組み、という意味合いである。

ハーネスには 2 つの層がある。

表 5.1 ハーネスの 2 つの層

層

内容

作る人

内側のハーネス

システムプロンプト、組み込みのツール、エージェントループ、権限の仕組み

Claude Code などのエージェント製品の開発者

外側のハーネス

規約ファイル、テスト、リンター、型検査、フック、権限の設定、CI、追加のツール

エージェントを使う開発者（本書の読者）

本書が主に扱うのは、外側のハーネスである。同じエージェント製品を使っていても、外側のハーネスの出来によって、得られる結果は大きく変わる。

ハーネスの考え方は、「エージェントが誤りを犯したら、その誤りが二度と起きない仕組みを作る」と要約できる [Hashimoto2026]。誤りのたびにプロンプトで注意するのではなく、規約ファイルに追記する、検査を追加する、ツールを用意するといった形で、仕組みとして解決する。

5.2. エージェントの基本構造

図 5.1 は、エージェントの基本構造である。モデルは、ハーネスから受け取ったコンテキストをもとに、次の行動（テキストの応答またはツール呼び出し）を決める。ハーネスはツールを実行し、その結果を次のコンテキストに加えてモデルに返す。

5.3. ガイドとセンサー

外側のハーネスの仕組みは、働きによって 2 種類に分けられる [Bockeler2026]。

  • ガイド：エージェントが行動する前に、正しい方向へ導く仕組み。規約ファイル、手順書、コードの雛形、型定義など。最初の試行で正しい結果が出る確率を上げる。

  • センサー：エージェントが行動した後に、結果を観測して誤りを知らせる仕組み。テスト、型検査、リンター、レビューなど。エージェントが自分で誤りに気付き、修正できるようにする。

ガイドだけでは、規則が実際に守られたかを確かめられない。センサーだけでは、同じ誤りを毎回繰り返し、修正に時間がかかる。両方を組み合わせる必要がある。

さらに、それぞれを「計算による仕組み」と「推論による仕組み」に分けられる。

表 5.2 ガイドとセンサーの分類

計算による仕組み（決定的）

推論による仕組み（LLM を使う）

ガイド

型定義、コードの雛形、プロジェクトの生成ツール

規約ファイル、手順書、設計文書

センサー

テスト、型検査、リンター、ビルド、構造の検査

AI によるコードレビュー、LLM による採点

計算による仕組みは速く、結果が確実で、変更のたびに実行できる。推論による仕組みは遅く、費用がかかり、結果が揺らぐが、意味的な判断（設計の妥当性など）ができる。まず計算による仕組みで確かめられることを最大限に確かめ、残りを推論による仕組みと人間が補う、という順序で考えるとよい。

5.4. ツールの設計

エージェントに独自のツールを提供する場合（後述する MCP サーバーを作る場合を含む）には、ツールの設計が結果を左右する [Anthropic-Tools]。

  • 名前と説明を明確にする：モデルは名前と説明だけを見て、ツールを使うかどうか、どう使うかを判断する。何をするツールか、いつ使うべきか、引数の意味と形式を説明に書く。

  • 粒度を作業に合わせる：API の各エンドポイントをそのままツールにするより、「顧客の注文履歴を取得する」のように、エージェントが行いたい作業の単位でツールを作るほうが、呼び出しの回数と誤りが減る。

  • 出力を絞る：大量の出力はコンテキストを圧迫する。必要な項目だけを返す、件数を制限する、ページ分割するなどの工夫をする。

  • エラーを行動につながる文章で返す：「エラー: 404」ではなく、「ファイル config.toml は存在しない。list_files でファイル名を確認すること」のように、原因と次に取るべき行動を返す。

外部のツールやデータを接続するための標準規格として MCP（Model Context Protocol）がある [MCP]。MCP に対応したエージェントであれば、課題管理サービス、データベース、ブラウザの操作などを、MCP サーバーを登録するだけで使えるようになる。ただし、ツールを増やすほどツール定義がコンテキストを占め、ツールの選択も誤りやすくなる。使うものだけを登録する。

5.5. サンプルコード：最小のエージェント

コード 5.1 は、ツールを使う最小のエージェントである。

コード 5.1 ツールを使う最小のエージェント（ex03_tool_agent.py）
  1"""ツールを使う最小のエージェントの例。
  2
  3モデルの応答にツール呼び出しが含まれていればツールを実行し、結果を会話履歴に
  4追加して再びモデルを呼ぶ。ツール呼び出しがなくなったら、その応答を最終回答とする。
  5ツールの失敗は例外にせず、モデルが読んで次の行動を選べる文章として返す。
  6"""
  7
  8from __future__ import annotations
  9
 10import re
 11from collections.abc import Callable, Sequence
 12from dataclasses import dataclass
 13
 14from llm_stub import LLMClient, Message, Response, RuleBasedLLM, ToolCall
 15
 16
 17@dataclass(frozen=True)
 18class Tool:
 19    """モデルに提供するツール。parameters は引数名と説明の対応。"""
 20
 21    name: str
 22    description: str
 23    parameters: dict[str, str]
 24    func: Callable[[dict[str, str]], str]
 25
 26
 27class ToolRegistry:
 28    """ツールの登録・説明文の生成・実行を受け持つ。"""
 29
 30    def __init__(self, tools: Sequence[Tool]) -> None:
 31        self._tools = {t.name: t for t in tools}
 32
 33    def describe(self) -> str:
 34        """システムプロンプトに含めるツールの説明を返す。"""
 35        lines = ["# 使えるツール"]
 36        for t in self._tools.values():
 37            params = ", ".join(f"{k}: {v}" for k, v in t.parameters.items())
 38            lines.append(f"- {t.name}({params}): {t.description}")
 39        return "\n".join(lines)
 40
 41    def execute(self, call: ToolCall) -> str:
 42        tool = self._tools.get(call.name)
 43        if tool is None:
 44            return f"エラー: ツール {call.name} は存在しない。使えるツール: {', '.join(self._tools)}"
 45        missing = [p for p in tool.parameters if p not in call.arguments]
 46        if missing:
 47            return f"エラー: 引数 {', '.join(missing)} が不足している"
 48        return tool.func(call.arguments)
 49
 50
 51def run_agent(llm: LLMClient, system: str, task: str, registry: ToolRegistry, max_turns: int = 8) -> str:
 52    """エージェントループ。max_turns 回モデルを呼んでも終わらなければ打ち切る。"""
 53    messages: list[Message] = [Message("user", task)]
 54    full_system = f"{system}\n\n{registry.describe()}"
 55    for turn in range(1, max_turns + 1):
 56        response = llm.complete(full_system, messages)
 57        messages.append(Message("assistant", response.text, response.tool_calls))
 58        if not response.tool_calls:
 59            return response.text
 60        for call in response.tool_calls:
 61            result = registry.execute(call)
 62            print(f"[{turn}] {call.name}({call.arguments}) -> {result[:60]}")
 63            messages.append(Message("tool", result, tool_call_id=call.call_id))
 64    return f"{max_turns} 回で完了しなかったため打ち切った"
 65
 66
 67# ---- ツールの実装（ファイルシステムの代わりに辞書を使う） ----
 68
 69FILES = {
 70    "README.md": "サンプルアプリ。設定は config/ 配下にある。",
 71    "config/app.toml": "[server]\nport = 8080\ntimeout = 30\n",
 72    "src/main.py": "print('hello')\n",
 73}
 74
 75
 76def list_files(args: dict[str, str]) -> str:
 77    prefix = args["prefix"]
 78    names = [n for n in FILES if n.startswith(prefix)]
 79    return "\n".join(names) if names else f"{prefix} で始まるファイルはない"
 80
 81
 82def read_file(args: dict[str, str]) -> str:
 83    path = args["path"]
 84    if path not in FILES:
 85        return f"エラー: {path} は存在しない。list_files でファイル名を確認すること"
 86    return FILES[path]
 87
 88
 89# ---- モデルの代わり：直前のツール結果を読んで次の行動を決める ----
 90
 91def agent_rule(system: str, messages: Sequence[Message]) -> Response:
 92    last = messages[-1]
 93    if last.role == "user":
 94        # 推測したパスを読みに行く（ここでは誤ったパスを推測する）
 95        return Response("設定ファイルを読む", (ToolCall("c1", "read_file", {"path": "config.toml"}),))
 96    if last.content.startswith("エラー"):
 97        return Response("ファイル一覧を確認する", (ToolCall("c2", "list_files", {"prefix": "config/"}),))
 98    if last.content.startswith("config/"):
 99        path = last.content.splitlines()[0]
100        return Response("見つかったファイルを読む", (ToolCall("c3", "read_file", {"path": path}),))
101    match = re.search(r"timeout = (\d+)", last.content)
102    if match:
103        return Response(f"timeout の設定値は {match.group(1)} 秒である（config/app.toml）。")
104    return Response("timeout の設定は見つからなかった。")
105
106
107def main() -> None:
108    registry = ToolRegistry([
109        Tool("list_files", "指定した接頭辞で始まるファイルの一覧を返す", {"prefix": "パスの接頭辞"}, list_files),
110        Tool("read_file", "ファイルの内容を返す", {"path": "ファイルのパス"}, read_file),
111    ])
112    answer = run_agent(
113        RuleBasedLLM(agent_rule),
114        system="あなたはリポジトリを調査するエージェントである。",
115        task="サーバーの timeout の設定値を調べて",
116        registry=registry,
117    )
118    print(f"最終回答: {answer}")
119
120
121if __name__ == "__main__":
122    main()

  • ToolRegistry（27 〜 48 行目）は、ツールの説明文の生成と実行を受け持つ。存在しないツールや引数の不足は、例外ではなく、モデルが読める文章として返している。

  • run_agent（51 〜 64 行目）がエージェントループである。モデルの応答にツール呼び出しがあれば実行し、結果を履歴に加えて再びモデルを呼ぶ。ツール呼び出しがなくなったら終了する。max_turns で反復の上限を設けている。

  • read_file（82 〜 86 行目）は、ファイルが見つからないとき、次に取るべき行動をエラーメッセージに含めている。

  • agent_rule（91 〜 104 行目）は、モデルの代わりに、直前のツールの結果を読んで次の行動を決める。

実行結果は次のとおりである。最初に誤ったパスを読もうとして失敗するが、エラーメッセージの指示に従ってファイルの一覧を確認し、正しいファイルにたどり着いている。

コード 5.2 ex03_tool_agent.py の出力
1[1] read_file({'path': 'config.toml'}) -> エラー: config.toml は存在しない。list_files でファイル名を確認すること
2[2] list_files({'prefix': 'config/'}) -> config/app.toml
3[3] read_file({'path': 'config/app.toml'}) -> [server]
4port = 8080
5timeout = 30
6
7最終回答: timeout の設定値は 30 秒である（config/app.toml）。

5.6. センサーとしての検証手段

コーディングエージェントにとって最も重要なハーネスは、エージェント自身が実行できる検証手段である。人間が「動かしてみたら壊れていた」と伝える代わりに、エージェントが自分でテストを実行し、失敗を見て修正できれば、人間の手を介さずに品質を上げられる。

表 5.3 主な検証手段

手段

検出できるもの

備考

型検査

存在しない属性や関数の使用、型の不一致

ハルシネーションによる誤りの多くを、実行前に検出できる

リンター

未使用の変数、危険な書き方、規約違反

独自の規則を追加すると、プロジェクト固有の規約も機械的に守らせられる

単体テスト

関数やクラスの振る舞いの誤り

速く実行できるため、変更のたびに実行させる

結合テスト、E2E テスト

部品をつないだときの誤り、画面の操作の誤り

時間がかかるため、作業の区切りで実行させる

ビルド、CI

環境の差による誤り、他の変更との衝突

最後の砦として、人間のレビューの前に実行する

検証手段は、次の性質を満たすほど、エージェントにとって使いやすい。

  • 1 つのコマンドで実行できる：手順が複雑だと、エージェントは実行を省略したり、誤った方法で実行したりする。

  • 速い：数秒で結果が出れば、変更のたびに実行できる。

  • 結果が安定している：実行のたびに結果が変わる不安定なテストは、エージェントを誤った修正に導く。

  • メッセージが具体的である：どこが、なぜ、どう間違っているかが分かるメッセージは、修正の手がかりになる。リンターの独自規則では、エラーメッセージに修正の方法まで書いておくと効果的である。

5.7. 権限とサンドボックス

エージェントにファイルの編集やコマンドの実行を任せる以上、誤った操作や悪意ある指示による被害を防ぐ仕組みが必要である。

  • 権限の設定：許可なしで実行してよい操作（テストの実行など）、確認を求める操作（ファイルの編集など）、禁止する操作（本番環境への接続、秘密情報の読み取りなど）を区別する。

  • サンドボックス：エージェントが動く環境を、コンテナや仮想マシンなどで隔離し、ファイルシステムやネットワークへのアクセスを制限する。自律的に長時間動かす場合には、特に重要である。

  • 承認：取り消せない操作（本番へのデプロイ、データの削除、外部への送信など）は、人間の承認を必須にする。

権限を最初から広く与えるのではなく、エージェントの振る舞いを確認しながら、信頼できる操作から段階的に許可していくのが安全である。

5.8. フック

フックは、エージェントの動作の特定の時点（ツールを使う前後、応答を終える時など）で、指定した処理を自動的に実行する仕組みである。

規約ファイルに書いた指示は、モデルが判断して従うものであり、守られないことがある。フックは、モデルの判断と関係なく必ず実行される。「ファイルを編集したら必ず整形する」「秘密情報を含むファイルへの書き込みを止める」のように、例外なく守らせたい規則はフックで実現する。フックは、決定的なガイドとセンサーを、エージェントの動作の中に組み込む手段だといえる。具体的な設定は実践：Claude Code で示す。

5.9. AI が働きやすいリポジトリ

ハーネスを整えやすいかどうかは、リポジトリそのものの性質にも左右される。人間の新しいメンバーが参加しやすいリポジトリは、AI にとっても働きやすい。

表 5.4 AI が働きやすいリポジトリの性質

性質

理由

型が付いている

型検査が強力なセンサーになる。型そのものがガイドとして、関数の使い方を伝える

テストが充実している

変更が既存の振る舞いを壊していないかを、エージェント自身が確かめられる

構造が一貫している

既存のコードを手本にでき、どこに何を書けばよいかを推測しやすい

環境構築とビルドが自動化されている

エージェントが環境を再現でき、実行結果が人間の環境と一致する

判断の理由が文書化されている

コードから読み取れない「なぜ」を、エージェントが参照できる

逆に、テストがなく、手作業の手順が多く、暗黙の決まりが多いリポジトリでは、エージェントは誤りに気付けず、人間の確認の負担が大きくなる。AI を活用するための投資は、そのまま人間にとっての開発のしやすさにもつながる。
