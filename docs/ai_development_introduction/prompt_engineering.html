3. プロンプトエンジニアリング

3.1. 本書の定義

プロンプトエンジニアリングとは、LLM への指示文（プロンプト）を工夫して、意図した出力を得る技術である。4 つの層のうち最も内側にあり、他のすべての層の土台になる。エージェントを使う場合でも、最終的にモデルに届くのはテキストであり、その書き方の良し悪しが結果を左右する。本章の内容は、各 AI 企業が公開しているプロンプトの指針 [Anthropic-Prompt] などを、開発作業の観点で整理したものである。

3.2. プロンプトの構成要素

よいプロンプトには、表 3.1 の要素が含まれていることが多い。すべてを毎回書く必要はないが、出力が期待と違うときは、どの要素が欠けているかを確認するとよい。

多くの API や対話型 AI では、プロンプトをシステムプロンプトと、利用者からのメッセージ（ユーザーメッセージ）に分けて渡せる。システムプロンプトには会話全体を通じて変わらない役割・制約・出力形式を、ユーザーメッセージには個々のタスクと入力を書くのが一般的である。

3.3. 基本的なテクニック

3.3.1. 明確かつ具体的に書く

モデルは、書かれていないことを推測で補う。推測が外れないよう、対象・範囲・完了の条件を具体的に書く。目安は「このプロジェクトを知らない優秀な同僚に依頼する文面として十分か」である。

表 3.2 曖昧な指示と具体的な指示

曖昧な指示

具体的な指示

テストを書いて

src/order.py の calculate_total に、割引率が 100% の場合と数量が 0 の場合のテストを tests/test_order.py に追加して。既存のテストの書き方に合わせること

このコードを速くして

load_users は 1 万件で 8 秒かかる。プロファイルの結果では DB への問い合わせが件数分発生している。問い合わせを 1 回にまとめて、1 秒以内にしたい

いい感じにリファクタリングして

report.py の export 関数（約 200 行）を、データの取得・整形・出力の 3 つの関数に分割して。外部から見た振る舞いは変えず、既存のテストがすべて成功すること

3.3.2. 理由を伝える

制約には理由を添える。「float を使うな」とだけ書くより、「金額の計算で丸め誤差が出るため float ではなく Decimal を使う」と書くほうが、モデルは規則の意図を理解し、明示していない似た場面にも正しく適用しやすい。

3.3.3. 例を示す

期待する出力の例をいくつか示すと、出力の形式や判断の基準がそろいやすい。例を含むプロンプトを few-shot プロンプトと呼ぶ [Brown2020]。例は、典型的なものだけでなく境界的なものも含め、互いに十分異なるものを選ぶ。似た例ばかりだと、モデルが例の表面的な特徴（文の長さや言い回し）まで真似てしまう。

3.3.4. 考える手順を与える

複雑な問題では、答えを出す前に考える過程を書かせると精度が上がることが知られており、これを Chain-of-Thought という [Wei2022]。現在の主要なモデルの多くは、回答の前に内部で推論する機能（拡張思考、推論モードなど）を備えているため、「段階的に考えよ」と書く必要性は以前より小さい。それでも、「まず原因の候補を列挙し、次にそれぞれをログと照合し、最後に最も可能性の高いものを選ぶ」のように、作業の手順を示すことは有効である。

3.3.5. 入力と指示を区別する

長い入力を含めるときは、XML 風のタグや見出しで指示と入力を区切る。区切りがないと、入力の中の文（例えばレビュー対象のコードのコメント）を指示と取り違えることがある。入力が信頼できない外部のデータである場合には、この区別はセキュリティ上も重要になる（リスクと品質管理参照）。

3.3.6. 出力形式を指定する

出力をプログラムで処理する場合は、JSON などの形式と、含めるキーを明示する。多くの API は、出力が指定した JSON スキーマに必ず従うようにする構造化出力の機能を備えている。プログラムで処理する用途では、プロンプトでの指定よりも構造化出力を使うほうが確実である。

3.3.7. してほしいことを書く

「Markdown を使うな」のような否定形の指示より、「段落に分けた平文で書け」のように、望む状態を肯定形で書くほうが伝わりやすい。禁止事項が必要な場合は、代わりにどうすべきかを併記する。

3.4. サンプルコード：プロンプトのテンプレート

コード 3.1 は、プロンプトの構成要素を別々に管理し、システムプロンプトとユーザーメッセージを組み立てる例である。構成要素を分けておくと、どの要素を変えたときに出力がどう変わるかを比較しやすい。この比較を体系的に行う方法は評価駆動開発で説明する。

コード 3.1 プロンプトのテンプレート（ex01_prompt_template.py）
 1"""プロンプトの構成要素を組み立てるテンプレートの例。
 2
 3役割・制約・出力形式をシステムプロンプトに、タスク・例・入力を
 4ユーザーメッセージに配置する。構成要素を分けて管理すると、
 5どの要素を変えたときに出力がどう変わるかを比較しやすくなる。
 6"""
 7
 8from __future__ import annotations
 9
10from dataclasses import dataclass
11
12
13@dataclass(frozen=True)
14class Example:
15    """入力と期待する出力の組（few-shot の例）。"""
16
17    input: str
18    output: str
19
20
21@dataclass(frozen=True)
22class PromptSpec:
23    """プロンプトの構成要素。"""
24
25    role: str
26    task: str
27    constraints: tuple[str, ...] = ()
28    examples: tuple[Example, ...] = ()
29    output_format: str = ""
30
31
32def build_system_prompt(spec: PromptSpec) -> str:
33    """役割・制約・出力形式からシステムプロンプトを組み立てる。"""
34    lines = [spec.role]
35    if spec.constraints:
36        lines.append("")
37        lines.append("# 制約")
38        lines.extend(f"- {c}" for c in spec.constraints)
39    if spec.output_format:
40        lines.append("")
41        lines.append("# 出力形式")
42        lines.append(spec.output_format)
43    return "\n".join(lines)
44
45
46def build_user_prompt(spec: PromptSpec, input_text: str) -> str:
47    """タスク・例・入力からユーザーメッセージを組み立てる。
48
49    入力や例は XML 風のタグで囲み、指示と区別できるようにする。
50    """
51    parts = [spec.task]
52    if spec.examples:
53        parts.append("<examples>")
54        for ex in spec.examples:
55            parts.append(f"<example>\n<input>{ex.input}</input>\n<output>{ex.output}</output>\n</example>")
56        parts.append("</examples>")
57    parts.append(f"<input>\n{input_text}\n</input>")
58    return "\n".join(parts)
59
60
61def main() -> None:
62    spec = PromptSpec(
63        role="あなたは Python のコードレビューを担当するシニアエンジニアである。",
64        task="次の関数をレビューし、不具合の可能性がある箇所を指摘せよ。",
65        constraints=(
66            "指摘は不具合に限定し、命名やスタイルには触れない",
67            "根拠となる入力例を必ず添える",
68            "問題がなければ「指摘なし」とだけ答える",
69        ),
70        examples=(
71            Example(
72                input="def head(xs: list[int]) -> int:\n    return xs[0]",
73                output='[{"line": 2, "issue": "空リストで IndexError", "input": "[]"}]',
74            ),
75        ),
76        output_format='JSON 配列で返す。各要素は "line"、"issue"、"input" の 3 つのキーを持つ。',
77    )
78    code = "def average(xs: list[float]) -> float:\n    return sum(xs) / len(xs)"
79
80    print("===== システムプロンプト =====")
81    print(build_system_prompt(spec))
82    print()
83    print("===== ユーザーメッセージ =====")
84    print(build_user_prompt(spec, code))
85
86
87if __name__ == "__main__":
88    main()

役割・制約・出力形式はシステムプロンプトに（32 〜 43 行目）、タスク・例・入力はユーザーメッセージに配置している（46 〜 58 行目）。例と入力は XML 風のタグで囲み、指示と区別している。実行すると、次のプロンプトが出力される。

3.5. 開発作業でのプロンプトの例

開発作業の種類ごとに、プロンプトに含めるべき情報をまとめる。

表 3.3 開発作業ごとにプロンプトに含める情報

作業

含める情報

実装

実現したい振る舞い、対象のファイルやモジュール、従うべき既存の設計、完了条件（どのテストが成功すればよいか）

リファクタリング

変えてよいもの（内部構造）と変えてはいけないもの（外部から見た振る舞い、公開 API）、確認の方法

レビュー

観点（不具合、セキュリティ、性能など）、指摘の粒度、重要度の付け方、指摘しなくてよいこと

テストの作成

対象の関数、確かめたい条件（正常系、境界値、異常系）、使うテストフレームワークと既存のテストの書き方

デバッグ

期待した動作と実際の動作、エラーメッセージとスタックトレースの全文、再現手順、すでに試したこと

デバッグでは、エラーメッセージを要約せず、そのまま渡すことが特に重要である。人間が要約すると、原因の手がかりになる情報が落ちることが多い。

3.6. アンチパターン

表 3.4 プロンプトのアンチパターン

アンチパターン

問題

対策

曖昧な指示

モデルが推測で補い、意図と違う結果になる

対象・範囲・完了条件を明示する

矛盾する指示

「簡潔に」と「詳しく」のような指示が混在し、どちらかが無視される

優先順位を明示する。プロンプトを見直して矛盾を除く

過剰な強調

「絶対に」「必ず」を多用すると、その指示を過剰に適用し、他の指示との釣り合いが崩れる

強調は本当に重要な箇所に限り、理由を添える

詰め込みすぎ

1 つのプロンプトで多くの作業を頼むと、一部が抜け落ちる

作業を分割し、1 回の依頼で 1 つの目的に絞る

試行錯誤の放置

変更の効果を確かめずにプロンプトを書き換え続け、改善したのか悪化したのか分からなくなる

評価データを用意し、変更ごとに採点する（評価駆動開発）

3.7. プロンプトだけでは解決できないこと

プロンプトの工夫には限界がある。例えば、次のような問題は指示文をいくら工夫しても解決しない。

  • モデルがプロジェクトの規約や既存のコードを知らない。→ 必要な情報を渡す（コンテキストエンジニアリング）。

  • モデルが書いたコードが動くかどうか、モデル自身には分からない。→ テストを実行できる環境を与える（ハーネスエンジニアリング）。

  • 1 回で正しい答えにたどり着けない。→ 検証と修正を繰り返させる（ループエンジニアリング）。

このように、プロンプトエンジニアリングは外側の層と組み合わせて初めて力を発揮する。
