8. 評価駆動開発

8.1. 本書の定義

評価駆動開発とは、AI の出力の品質を測る評価（Evals）を先に用意し、プロンプト、コンテキスト、ハーネスの変更を、その評価の結果に基づいて判断する開発の進め方である。テスト駆動開発が「テストを先に書き、テストの成功を目指して実装する」のと同じように、評価駆動開発では「評価を先に用意し、評価の結果の改善を目指して AI の使い方を変える」。

AI の振る舞いは確率的であり、プロンプトや規約ファイルの小さな変更が、思わぬ箇所に影響することがある。数回試して「よくなった気がする」で判断していると、ある問題を直したつもりで別の問題を生んでいても気付けない。評価は、この「気がする」を数字に置き換える。

評価駆動開発が役立つ場面は、大きく 2 つある。

  • AI 機能を持つ製品の開発：分類、要約、抽出、対話などの機能の品質を測る。

  • AI を使った開発そのものの改善：規約ファイル、スキル、フックなど、自分たちのハーネスの変更が、コーディングエージェントの成果を本当に改善したかを測る。

コーディングの評価では、テストの実行による採点が中心になる。生成されたコードが、あらかじめ用意したテストに成功するかどうかで採点する方式である。公開されているベンチマークとして、実在する OSS の課題を解かせ、その課題のテストで採点する SWE-bench がよく知られている [Jimenez2023]。

LLM による採点は、強力なモデルに採点させると人間の判断とよく一致する一方で、長い回答を高く評価する、自分と似た出力を好むなどの偏りがあることも報告されている [Zheng2023]。LLM による採点を使う場合は、採点基準を具体的に書き、一部を人間が採点して一致度を確かめる。

8.4. 指標

出力が確率的な場合、1 回の試行の合否だけでは実力を測れない。そこで、複数回の試行の結果をまとめた指標を使う。

\(\mathrm{pass@}k\) は、\(k\) 回試行して 1 回以上成功する確率である。あるタスクを \(n\) 回試行して \(c\) 回成功したとき、次の式で推定する [Chen2021]。

\[\mathrm{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\]

この式の右辺の分数は、\(n\) 回の試行から \(k\) 回分を選んだとき、すべてが失敗である確率を表す。複数のタスクで評価する場合は、タスクごとの値を平均する。

これに対し、\(\mathrm{pass}^k\) は、\(k\) 回の試行がすべて成功する確率である [Anthropic-Evals]。1 回の試行の成功率を \(p\) とすると、\(p^k\) で見積もれる。例えば、成功率 75% のエージェントが 3 回連続で成功する確率は、\(0.75^3 \approx 0.42\) である。

表 8.3 指標の使い分け

指標

意味

重視する場面

\(\mathrm{pass@}k\)

\(k\) 回のうち 1 回でも成功すればよい

複数の案を生成し、人間やテストがよいものを選べる場面

\(\mathrm{pass}^k\)

\(k\) 回すべて成功する必要がある

毎回確実に成功してほしい場面（無人で動く自動化など）

成功率が 0 でなければ、\(k\) を増やすと \(\mathrm{pass@}k\) は 100% に近づき、\(\mathrm{pass}^k\) は 0% に近づく。同じエージェントでも、どちらの指標を見るかで評価が大きく変わるため、用途に合った指標を選ぶ。また、品質だけでなく、費用（トークン数）と所要時間も合わせて記録しておくと、モデルや設定の選択に役立つ。

8.5. 評価のサイクル

評価駆動開発は、図 8.1 のサイクルで進める。

  1. 失敗を集める：実際の利用で起きた失敗を記録する。評価ケースは、想像で作るより実際の失敗から作るほうが効果的である。

  2. 評価ケースにする：失敗した入力と、期待する結果の組を評価データに加える。最初から数百件を用意する必要はなく、実際の失敗から作った 20 〜 50 件程度でも始められる [Anthropic-Evals]。

  3. 変更する：プロンプト、規約ファイル、ツールなどを変更する。

  4. 評価を実行する：新しく加えたケースだけでなく、すべてのケースを採点する。以前は成功していたケースが失敗するようになっていないか（回帰）を確かめるためである。

  5. 比較して判断する：変更前と比べて改善していれば採用し、悪化していれば元に戻す。

このサイクルは、ループエンジニアリングで述べたハーネス改善のループを、定量的に回すための方法でもある。

8.6. サンプルコード：プロンプトの比較

コード 8.1 は、不具合報告の重大度を分類するプロンプトの 2 つの版を、同じ評価データで採点して比較する例である。

コード 8.1 プロンプトの比較（ex05_simple_eval.py）
 1"""プロンプトの 2 つの版を、同じ評価データで採点して比較する例。
 2
 3題材は不具合報告の重大度（high / medium / low）の分類である。
 4模擬モデルは、システムプロンプトに書かれた判定基準だけを手がかりに分類する。
 5そのため、判定基準を充実させた版のほうが正解率が上がる。
 6"""
 7
 8from __future__ import annotations
 9
10import re
11from collections.abc import Callable, Sequence
12from dataclasses import dataclass
13from math import comb
14
15from llm_stub import LLMClient, Message, Response, RuleBasedLLM
16
17
18@dataclass(frozen=True)
19class EvalCase:
20    input: str
21    expected: str
22
23
24CASES = [
25    EvalCase("保存ボタンを押すと入力したデータが消失する", "high"),
26    EvalCase("ログインできない利用者がいる", "high"),
27    EvalCase("決済時に二重に課金される", "high"),
28    EvalCase("一覧画面の表示に 10 秒かかる", "medium"),
29    EvalCase("CSV 出力で日付の形式が仕様と異なる", "medium"),
30    EvalCase("ヘルプのリンクが切れている", "low"),
31    EvalCase("ボタンの文言に誤字がある", "low"),
32]
33
34PROMPT_A = """不具合報告の重大度を high / medium / low のいずれかで答えよ。
35- high: 消失
36- low: 誤字
37"""
38
39PROMPT_B = """不具合報告の重大度を high / medium / low のいずれかで答えよ。
40- high: 消失, ログイン, 課金
41- medium: 秒, 形式
42- low: 誤字, リンク
43"""
44
45
46def classifier_rule(system: str, messages: Sequence[Message]) -> Response:
47    """システムプロンプトの「- 重大度: キーワード」の行を判定基準として使う。"""
48    report = messages[-1].content
49    for label, keywords in re.findall(r"^- (high|medium|low): (.+)$", system, flags=re.MULTILINE):
50        if any(k.strip() in report for k in keywords.split(",")):
51            return Response(label)
52    return Response("medium")  # 判断できないときの既定値
53
54
55def exact_match(output: str, expected: str) -> bool:
56    return output.strip().lower() == expected
57
58
59def evaluate(llm: LLMClient, system: str, cases: Sequence[EvalCase],
60             grader: Callable[[str, str], bool]) -> tuple[float, list[str]]:
61    """正解率と、失敗したケースの説明を返す。"""
62    failures = []
63    for case in cases:
64        output = llm.complete(system, [Message("user", case.input)]).text
65        if not grader(output, case.expected):
66            failures.append(f"{case.input!r}: 期待 {case.expected}, 出力 {output}")
67    return 1 - len(failures) / len(cases), failures
68
69
70def pass_at_k(n: int, c: int, k: int) -> float:
71    """n 回の試行のうち c 回成功したとき、k 回試して 1 回以上成功する確率の不偏推定量。"""
72    if n - c < k:
73        return 1.0
74    return 1 - comb(n - c, k) / comb(n, k)
75
76
77def main() -> None:
78    llm = RuleBasedLLM(classifier_rule)
79    for name, prompt in [("プロンプト A", PROMPT_A), ("プロンプト B", PROMPT_B)]:
80        accuracy, failures = evaluate(llm, prompt, CASES, exact_match)
81        print(f"{name}: 正解率 {accuracy:.0%}")
82        for f in failures:
83            print(f"    失敗 {f}")
84    print(f"pass@1 = {pass_at_k(10, 3, 1):.2f}, pass@5 = {pass_at_k(10, 3, 5):.2f}（10 回中 3 回成功）")
85
86
87if __name__ == "__main__":
88    main()

  • CASES（24 〜 32 行目）が評価データである。入力と期待結果の組を並べている。

  • classifier_rule（46 〜 52 行目）は模擬モデルである。システムプロンプトに書かれた判定基準だけを手がかりに分類するため、判定基準の書き方によって結果が変わる。

  • exact_match（55 〜 56 行目）がコードによる採点器、evaluate（59 〜 67 行目）が評価の実行である。

  • pass_at_k（70 〜 74 行目）は、前述の \(\mathrm{pass@}k\) の式を実装したものである。

実行結果は次のとおりである。判定基準を充実させたプロンプト B では、すべてのケースで正解している。失敗したケースが一覧で出るため、次に何を直すべきかも分かる。

コード 8.2 ex05_simple_eval.py の出力
1プロンプト A: 正解率 57%
2    失敗 'ログインできない利用者がいる': 期待 high, 出力 medium
3    失敗 '決済時に二重に課金される': 期待 high, 出力 medium
4    失敗 'ヘルプのリンクが切れている': 期待 low, 出力 medium
5プロンプト B: 正解率 100%
6pass@1 = 0.30, pass@5 = 0.92（10 回中 3 回成功）

実際のモデルを使う場合は、同じプロンプトでも結果が揺らぐため、各ケースを複数回試行して集計する。

8.7. 注意点

  • 評価データへの過剰適合：評価データの個々のケースに合わせてプロンプトを調整し続けると、評価の点数は上がっても、評価データにない入力では性能が上がらないことがある。評価データの一部を調整に使わない確認用として取り分けておくとよい。

  • 採点器の誤り：採点器自体が誤っていると、評価の結果は意味をなさない。特に LLM による採点は、定期的に人間の採点と照らし合わせる。

  • 評価の陳腐化：エージェントの能力が上がると、既存の評価ケースはすべて成功するようになり、改善を測れなくなる。新しい失敗を継続的に評価データに加える。

  • 出力だけでなく過程も見る：エージェントの評価では、最終的な結果が正しくても、不要なファイルを変更した、テストを書き換えたなど、過程に問題がある場合がある。作業の記録（どのツールをどう使ったか）も確認する。
